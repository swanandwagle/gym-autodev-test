# OpenAPI Specification Conventions

This document defines the conventions every contributor must follow when adding
or modifying REST endpoints. The spec at `docs/openapi.yaml` is generated from
the running application and checked into the repository. CI fails when it drifts.

## Generating or regenerating the spec

The spec is generated by springdoc-openapi from the live Spring context.

**Regenerate after any controller change:**

```bash
# Option 1: test-driven regeneration (no running server needed — preferred)
mvn test -Dtest=OpenApiSpecDriftTest -Dopenapi.spec.regenerate=true

# Option 2: Maven plugin (requires a running server on port 8080)
mvn spring-boot:start springdoc-openapi:generate spring-boot:stop -Dspringdoc-openapi-maven-plugin.skip=false
```

The output is written to `docs/openapi.yaml`. Commit this file together with
your controller changes.

## CI drift check

`OpenApiSpecDriftTest` runs as part of `mvn test`. It boots the application
(using H2 in-memory, no Flyway) and compares the live-generated spec against
`docs/openapi.yaml`. If they differ, the build fails and the diff is shown.

## Error response conventions

Every endpoint **must** document each of its possible error responses.
Use the shared component schemas from `components/schemas` — never inline the
`ErrorEnvelope` structure.

### Mandatory responses for every endpoint

| Status | Code | When to document |
|--------|------|-----------------|
| 500    | `INTERNAL_ERROR` | All endpoints |

### Mandatory for endpoints that accept a request body (POST, PUT, PATCH)

| Status | Code | When to document |
|--------|------|-----------------|
| 400    | `MALFORMED_REQUEST` | Malformed JSON / unreadable body |
| 422    | `VALIDATION_FAILED` | Bean validation failure |

### Optional (add when the endpoint can return these)

| Status | Code | Trigger |
|--------|------|---------|
| 403    | `MEMBER_SUSPENDED` | Member account suspended |
| 403    | `MEMBER_INACTIVE`  | Member account inactive |
| 404    | `*_NOT_FOUND`      | Path-referenced resource missing |
| 409    | Various            | Business rule / state conflict |
| 422    | `INVALID_PAGINATION` | `page`/`size` out of range |
| 422    | `INVALID_SORT_FIELD` | `sort` field not allowed |

See `docs/error-catalogue.md` for the full list of codes and their HTTP statuses.

## The `errors[]` array

`errors[]` is present **only** on `422` responses. It is absent (not null, not
empty) on all other status codes. This is enforced by:

1. `GlobalExceptionHandler`: only populates `errors` when status is 422.
2. `ErrorEnvelope` record: field is `@JsonInclude(NON_NULL)`.
3. `OpenApiSpecValidationTest`: asserts `errors[]` does not appear on non-422 schemas.

In your OpenAPI annotations, reference the shared `ErrorEnvelope` component for
all error responses. Only the 422 response description should mention `errors[]`.

## Shared component schemas

The following schemas are defined once in `components/schemas` by `OpenApiConfig`
and must be referenced — not redefined — in every endpoint:

| Schema | Used for |
|--------|----------|
| `ErrorEnvelope` | All error responses (4xx, 5xx) |
| `FieldError` | Items in `errors[]` (422 only) |

Reference them in your `@ApiResponse` annotations:

```java
@ApiResponse(responseCode = "422", description = "Validation failed",
    content = @Content(schema = @Schema(ref = "#/components/schemas/ErrorEnvelope")))
@ApiResponse(responseCode = "404", description = "Resource not found",
    content = @Content(schema = @Schema(ref = "#/components/schemas/ErrorEnvelope")))
```

## Idempotency-Key header

`POST /api/v1/bookings` and `POST /api/v1/sessions/{id}/waitlist` accept:

```yaml
name: Idempotency-Key
in: header
required: false
schema:
  type: string
  maxLength: 64
description: >
  Optional client-supplied key (≤64 chars). Same member + same key → HTTP 200
  replay of original response. Same key + different sessionId → 409
  IDEMPOTENCY_KEY_CONFLICT.
```

## Pagination

All paginated list endpoints accept `PageParams` or `SortablePageParams`
via `@ParameterObject`. springdoc automatically expands them into individual
`page`, `size`, and `sort` query parameters. Do not redeclare them manually.

Response shape: `PageResponse<T>` — see `docs/error-status-semantics.md`.
